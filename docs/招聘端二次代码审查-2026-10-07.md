## 用户已确认的规则

- 平台额度读取失败，停止发送；自定义上限不能作为读取失败后的替代额度。
- 推荐候选人无需额外按 JD 或简历筛选；不新增筛选或分数门槛。
- 未勾选岗位的会话不应出现在候选人列表。
- 人工接管后需要在项目里编辑、确认发送普通回复。
- 不允许程序切换浏览器会话；非当前 Chrome 会话无法自动发送是该约束的结果，不作为切换功能 bug。
- 人工接管或暂停自动任务应允许手动回复；“停止联系”仍禁止人工及自动发送，不能借手动确认绕过。

## 已确认的代码问题

### 1. P1：停止招呼时状态写入失败，卡在 sending

位置：`service.py:278–280`、`jobs.py:195–198`。

服务捕获点击前取消后调用 `finish_greeting(uid, 'cancelled')`，但底层只接受 `sent` 和 `uncertain`，抛出 ValueError。实际结果是没有点击、记录却仍是 sending，后续外发被全局阻止。这属于上一轮停止修复漏检的接口不一致。

复现：模拟 verifier 在最终点击前抛 TaskCancelled；观察到“招呼结果必须是 sent 或 uncertain”，数据库仍是 sending。

修复方向：统一取消状态协议；只有确认没有提交点击的取消才能释放 sending。提交结果不确定时仍保持 uncertain。

### 2. P1：两个进程同时同步，会覆盖已经保存的新消息

位置：`service.py:528`、`:551`；`store.py:240–245`。

合并基于网络请求前读取的旧快照，最终写库没有重新读最新快照，也没有版本条件或同会话同步任务占用。Web 与 worker 的 RLock 不跨进程，因此“追加合并”仍可能丢消息。

复现：初始消息 1；慢任务读到 2，快任务读到 2、3 并先写库；慢任务再完成后，库中从 1、2、3 变成 1、2。没有假设消息 ID 连续，数字只作为合成唯一 ID。

修复方向：同一会话读取/写入跨进程串行，或在最终事务中与最新快照合并，避免旧快照覆盖。

### 3. P1：启动期间按停止，停止信号会被清掉

位置：`service.py:392–396`。

`start_discovery` 先等待额度读取，随后执行 `discovery_stop.clear()`。额度读取期间用户请求停止，读取完成后反而清除这次停止，启动后台循环。

复现：额度读取阻塞 → stop_discovery → 返回额度 → run_discovery 仍被调用，停止标志变为 false。

修复方向：开始新任务时建立独立任务代次/取消事件，初始化先于等待；后来的停止不能被启动逻辑清除。

### 4. P1：自定义模式首次任务跳过平台额度读取

位置：`service.py:302–306`、`:326–332`；`jobs.py:74–86`。

没有缓存额度时，custom 模式不会发起读取，直接将本地上限视为可用额度。因而第一次任务没有机会落实用户确认的“额度读取失败即停发”。已有过期缓存时会刷新，但首次运行和首次运行后的持续循环仍可完全不读取。

复现：自定义上限 10、无缓存、设置模拟额度读取失败；执行 run_discovery，额度读取方法调用次数为 0，推荐读取继续执行。

修复方向：所有模式启动及额度过期时均需可信平台额度；自定义额度只作为附加上限，不替代平台读取。

### 5. P1：负数 usedCount 被当成额外可用额度

位置：`local_session.py:446–452`。

解析只验证 limit 非负，不验证 used 非负；并且 isinstance(x, int) 会接受 bool。异常数据未被拒绝。

复现：HTTP 返回 limitCount=10、usedCount=-5，实际得到 remaining=15。该例验证的是异常字段处理，没有声称真实 BOSS 会返回负数。

修复方向：使用精确整数类型校验和非负约束；异常额度应拒绝读取，禁止把异常解释为可用额度。

### 6. P1：人工接管会禁止人工编辑和确认发送

位置：`service.py:861–862`、`:938–939`；`store.py:319–320`；`CandidateWorkspace.tsx:62`。

prepare_reply 无论手动文字还是模型回复均检查 taken_over；execute 和数据库 claim 也不区分手动与自动。用户已明确要求人工接管后能继续手动回复，而页面的人工输入保存按钮也未按 taken_over 禁用，点击后只得到报错。

复现：control(..., taken_over=True) 后保存明确的人工普通回复，被“当前会话已人工接管”拒绝。

修复方向：接管禁止自动任务；允许明确的人工草稿和确认发送。模型草稿在接管后的处理方式、停止联系权限应独立定义，不能直接解除所有限制。

### 7. P1：昨日待核实招呼阻止发送，但界面找不到该记录

位置：`jobs.py:210–211`；`GreetingConsole.tsx` 使用 `attempts` 显示记录和核实入口。

阻止逻辑查询所有日期的 sending/uncertain；记录列表只查询今天。跨日后旧记录仍全局阻止外发，却不在今天列表中，无法从该界面填写核实依据解除阻止。

复现：把一条 uncertain 招呼的日期改为过去；state.attempts 为空，但 blockers 提示存在待核实结果。

修复方向：今日计数和全日期待核实列表分开返回；核实入口覆盖所有未解决记录。

### 8. P1：候选人问题后跟系统消息，会永久漏掉自动回复

位置：`service.py:1243`、`:872–874`；`CandidateWorkspace.tsx:25–26`。

监测要求最后一条必须是候选人的 text；生成回复也只接受末条 incoming。候选人的问题之后出现平台系统记录，就不建立回复任务，后续没有新消息时也不会恢复。界面的“待回复”计数使用同一末条判断，也会隐藏该问题。

复现：新 incoming text 后追加一个 system 记录，连续两轮 monitor_once；prepare_reply 从未调用，reply_work 为空。

修复方向：以最近待处理的候选人消息及已回复/已处理游标判断，不让系统记录替代候选人问题；仍保留系统消息给模型上下文。

### 9. P2：触发禁发规则后，同一问题反复调用模型

位置：`service.py:892`、`:1267`；`policy.py:10–11`。

模型可能正确输出需要人工处理的面试提示，但 text 中含“面试”仍会被 check_reply 抛 PermissionError。监测只捕获 ValueError，pending 保留 waiting，下一轮再次生成。独立 worker 会按普通异常重试，连续三次后暂停整个监测。

复现：模型输出“面试事项交由人工确认。”且 needs_human=true；没有新消息，连续两轮仍调用模型 2 次。

修复方向：保存明确的本地待人工任务或终止原因，同输入不重试；保持外发禁令，不能为减少报错而放行邀约文字。

### 10. P2：同进程处理中，接管/关闭自动外发无法及时生效

位置：`api.py:82–85`；`service.py:571`、`:585`、`:928`；`RecruitingPage.tsx:48`；`CandidatePanels.tsx:19`。

控制操作和长读取/模型/外发持有同一服务锁。Web 进程执行“检查一次”或外发时，同进程的接管、停止联系、关闭自动外发会等待锁；前端 inFlight 也直接拒绝第二个操作，停止监测按钮在 busy 时不可用。

复现：持有服务锁时从另一线程请求 control，数据库 taken_over 保持 false，直到原操作释放锁。独立 worker 和 Web 是两个进程，Web 对 worker 写控制标志的路径不受这一内存锁影响；不能把此问题扩展成所有停止场景都无效。

修复方向：将停止类控制作为可并行落库的操作，再由任务提交前读取；前端允许停止请求越过普通 inFlight 队列。

### 11. P2：同一回复输入没有跨进程模型去重

位置：`service.py:866–877`。

评分有 SQLite 任务占用，回复生成只有各进程自己的 RLock。Web 和 worker 同时处理相同上下文时会各调用一次模型；相同文字最终可能被唯一约束合并，但费用已经发生，不同文字则产生多个草稿。

复现：两服务连接同一数据库并同时 prepare_reply；相同上下文模型被调用 2 次。本项没有声称已复现真实重复发送。

修复方向：按会话和输入签名建立持久化回复生成任务，抢占后再检查已存草稿。

### 12. P2：未勾选岗位的会话仍显示在候选人列表

位置：`service.py:65`；`CandidateWorkspace.tsx:23–26`。

后端返回所有会话，候选人页面默认“全部”只按姓名、岗位和状态筛选，未应用 published_jobs.selected。自动任务会排除未勾选岗位，但列表仍显示，违背用户刚确认的展示规则。

复现：清空勾选后，自动允许会话为空；state.conversations 仍包含原候选人，默认前端 list 条件继续包含该候选人。

修复方向：候选人工作列表应用明确的岗位选择规则；历史记录和全局待核实动作仍需可找到，不能因隐藏候选人而丢失核实入口。

### 13. P2：更换模型后，界面仍把旧评分显示为当前有效

位置：`CandidatePanels.tsx:15`；`service.py:841–845`。

后端有效评分检查包含 input_hash，覆盖模型配置等输入；前端 currentAssessment 只比较 document_id、position_id、position_version，未使用同一有效性口径。更换模型或凭据后，Agent 不使用旧评估，但页面仍显示旧分数并宣称当前有效评估。

复现：用 synthetic-old 生成合成评估，配置改为 synthetic-new；reply_context.assessment 为 None，而执行真实前端 currentAssessment 函数仍选出 synthetic-old。

修复方向：后端明确返回当前有效 assessment ID，由所有界面统一采用；不把凭据或凭据哈希传给前端。

## 处理不完整的功能：混合 PDF 扫描页不会进入 OCR

位置：`local_session.py:282`。

只有整个 PDF 的所有页都没有文字时才启用 OCR。若第一页有文字、第二页是扫描图片，则第二页不做 OCR，只记录 empty_pages 和占位提示。complete=false 保留，因此不是错误声称完整，但这一常见混合文档无法按现有 OCR 路径读全。

复现：两个合成页面分别返回文字和空文字，_ocr_pdf_or_raise 未调用，empty_pages=[2]。真实图片上的识别精度不在本次验证范围。

修复方向：按页判断并识别缺文字页，记录 OCR 页和失败页；继续保留人工完整性核对。

## 已明确、不得作为 bug 修改的约束

用户进一步确认：人工接管或暂停自动任务允许手动回复；停止联系仍禁止发送。因此手动权限修复不能放开停止联系。无需新增候选人筛选；禁止切换浏览器会话。未实现的被动监听、跨日调度等不计入上述代码 bug。非当前浏览器会话只能留草稿待人工打开，这是禁止切换的明确结果，应据实显示，不自动切换。
