## 优先处理的具体缺口

### P1：实际浏览器目标仍可能错误

位置：`recommend.py:145`、`:157`、`:193`。

虽然查到了指定 target ID，但 `_recommend_page` 随后使用 `p.url == target['url']` 找页面。两个推荐页 URL 一样时，取到的是第一个页面，无法保证是绑定的 target。隔离复现中，配置绑定第二页，实际返回第一张同 URL 页面。

应直接按 CDP target 身份映射页面，并固定调试实例；每次操作不能重新选首个可用端口。`contexts[0]` 也应与目标所属 context 一致。主动招呼和普通回复还应核对浏览器招聘账号与本地绑定账号一致，而不只核对候选人 ID、标题和岗位 ID。

### P1：岗位授权没有覆盖事务与全部自动处理

位置：`service.py:230`、`jobs.py:128`、`service.py:1027`。

单次招呼先检查岗位，之后再预占；预占事务只检查预算与待核实记录，不查 published_jobs.selected/status。两个进程之间可以发生“检查通过 → 另一进程取消勾选 → 原进程占用并点击”。隔离复现直接取消勾选后调用事务入口，仍成功插入发送占用。

多人监测只查 positions.enabled，不查 published_jobs。新建 positions 的 enabled 默认为 1。未关联平台岗位的 context 会话和已取消勾选的 boss 岗位会话都能进入自动队列，隔离复现已确认。

应定义一份统一的岗位可处理判定，预占事务、监测、评分与自动外发全部使用。待关联岗位不能仅靠填了 JD 就视为已授权。发送前还需检查授权是否在模型生成或网络等待期间撤销。

### P1：额度跨日、TTL 与读取基线仍不完整

位置：`service.py:189`、`:353`、`jobs.py:55`、`:165`。

1. `start_discovery` 在进入能刷新额度的 `run_discovery` 前先检查 blockers。昨天的额度记录导致启动报“未读取或已过期”，刷新调用次数为 0。首次未读取额度也有同类先后顺序问题。
2. `_quota_blocked` 和 `state()` 对 unlimited 先放行，没有先验证日期及读取时间。隔离复现将日期设为 2000 年，仍无额度阻塞。
3. TTL 刷新只在平台模式循环的部分位置检查。单次招呼及自定义模式也会依赖同日旧平台数据；长时间处理同一岗位时，TTL 不一定及时生效。
4. `read_greeting_quota` 先发 HTTP，返回后才取本地 attempted 作基线。若响应代表发送前的平台值，但另一进程在请求期间已完成一次发送，该次占用会被算进“读取时已有”，从而漏扣。复现：平台读得剩余 1，期间本地发送 1，最终仍显示剩余 1。

应明确额度观测与发送占用的同步规则，处理读取期间的 in-flight 操作；日期、TTL 和 unlimited 一起验证。自定义模式允许未知平台额度与否需要明确产品规则，不能把未知显示成可信余额。

### P1：普通回复的跨进程发送边界有遗漏

位置：`store.py:237`、`service.py:815`、`:994`、`:1008`。

`claim` 只占用某个 outbox ID，没有按账号/会话限制其他 sending/uncertain。隔离复现：第一次回复发送异常转 uncertain，另建一条草稿仍能发送，浏览器方法共执行两次。

自动回复每日计数也不是“检查额度 + 占用任务 + 加计数”的一个数据库事务；两个服务可同时通过最后一个额度检查。`RLock` 只在单进程单服务内有效，不能协调 Web 与 worker。

`_auto_send_if_allowed` 在 execute 返回 uncertain 时仍记录 auto_sent，并返回 True，事件可能与实际发送状态矛盾。需按确认状态记录事件。

建议以会话为单位建立持久化外发互斥，按已约定范围阻止待核实后的后续动作；将自动回复额度占用放进事务，并在最终点击前重新核对停止、接管、自动外发开关和资料版本。

### P1：恢复逻辑可能误判另一个进程的活动任务

位置：`jobs.py:35`、`store.py:233`。

每创建 RecruitingJobs 就把所有 sending 改成 uncertain；每创建 RecruitingService 又会 recover_outbox。Web 和 worker 使用同一数据库时，新服务不能等价于“旧任务进程已经死掉”。

隔离复现：第一服务预占 sending，第二服务初始化后记录变 uncertain；原服务确认成功后，finish_greeting 只更新 sending，因此不能把记录改回 sent。

需记录任务 owner、租约/心跳与失效时间，只恢复已失去执行者的任务。招呼的 uncertain 当前也没有明确的核实/解除 API 和界面流程，正常恢复不能要求用户手工修改 SQLite。

### P1：评分仍可能跨进程重复调用模型

位置：`service.py:663`、`:683`。

评分唯一索引只保证最终存储一条结果。实际模型调用发生在 INSERT OR IGNORE 之前，进程内锁无法防止另一服务重复调用。

隔离复现：两个 RecruitingService 共用数据库、同一资料和模型配置，同时 assess；模型方法调用 2 次，数据库最终只有 1 条评估。

应在调用模型之前事务性占用 input_hash，带任务状态、owner 和超时恢复；附件下载同样需要数据库级占用。已有同进程多线程测试不能代替两个服务/进程的测试。

### P1：增量无新消息分支引入新回归

位置：`local_session.py:127`、`service.py:499`。

`read_conversation` 在解析身份前就返回 None。复现中，历史消息的招聘账号已不是 expected_account，但 mid 没变化，方法仍返回 None，不触发身份不一致暂停。

`sync` 收到 None 后立即返回，跳过 process_received_resume。缺模型/JD的简历在后来补齐配置、没有新聊天消息时，不会按原承诺自动评分；已有 JD/模型变化也不会自动重评，首次附件失败后待处理状态可能被跳过。复现中无新消息时简历处理方法调用 0 次。

无新消息只应跳过消息写入和新回复生成，不能跳过账号健康核实与已有简历的状态推进。相应既有简历测试使用的模拟会话通常返回快照，没有覆盖真实的 None 分支。

### P1：发送前重读会覆盖已保存历史

位置：`service.py:464`、`:815`。

增量 sync 使用追加合并，但 execute 的发送前 HTTP 重读直接 import_conversation(source)。平台已删除或当前不再返回的旧消息会被从本地快照覆盖掉，破坏“已读历史留在本地”的目标。

隔离复现：本地已有两条消息，平台只返回最新一条；发送检查被阻止，但数据库旧历史仍从两条变一条。应统一消息合并路径，分别记录历史留存、当前可见范围、编辑/撤回状态和用于外发的版本核对依据。

### P1：停止边界没有贯穿当前任务

位置：`service.py:683`、`:747`、`:815`、`:925`、`local_session.py:86`。

隔离复现把 stop_event 先设置，再调用 assess，仍进入模型一次。auto_assess、resume 等路径没有统一停止检查。

关闭监测只改 DB 标志，不会唤醒传入 LocalBossSession 的 stop_event；当前 HTTP/附件/模型链中未持续检查 monitor_enabled。execute 在长 HTTP 复核之后直接 claim/操作浏览器，也缺少最后一个完整状态守卫。招呼节流调用 `throttle.wait()` 不传 discovery_stop，停止只能等到睡眠结束。

应统一取消上下文：任务开始、每次请求前、分页等待后、模型前后和最后点击前检查，并让监测开关取消当前任务。已经发出的 HTTP/模型请求可能只能等超时结束；验收应要求取消后不再发起后续动作，不承诺撤回已提交操作。

### P2：岗位关联及增量覆盖范围仍需补齐

位置：`store.py:171`、`browser.py:156`、`local_session.py:150`。

已有会话始终保留 old.position_id，不会根据新核实的平台 ID重新关联或拒绝变更。隔离复现：会话标题不变、平台 ID 从 j1 改 j2，仍关联 boss-j1。原有同名共用记录也没有存量迁移。平台 JD 读取仅按标题判断，两个同名岗位仍可能读错 JD。

增量读取假定 mid 可用于“比本地最大 ID 新”的判断，且页面按 ID 降序排列；遇到 mid <= since_mid 就 break。合成升序响应 [6,7]、游标 6 会跳过新消息 7并报身份核实失败。这是输入健壮性和平台契约验证缺口，本次没有证明真实 BOSS 当前返回升序或 mid 非单调，不能据此声称真实生产已漏消息。

仍需记录首次绑定/断线恢复的覆盖边界、重叠消息、平台响应排序和增量游标契约；仅做 mid 大小过滤不等于已证明断线后补齐。

### P2：监测吞错、联系人完整性和状态文案

位置：`service.py:410` 的 `_friend_job_map`、`browser.py:133`、`service.py:1008`、前端 `CandidatePanels.tsx:16`。

- `_friend_job_map` 捕获 AccountPauseError 后返回空字典，绑定导入可继续；验证码/身份问题未必到达 worker 的暂停分支。资料暂缺与账号必须暂停应分开。
- 联系人滚动至 DOM 数量连续三次不变，不足以证明全账号完整。虚拟列表可能复用 DOM，网络慢时也可能提前稳定；200 次循环耗尽后同样没有明确 incomplete 状态。导入结果不应无条件标“全账号”。
- 当前每 120 秒处理一个会话；N 个允许会话的巡回时间至少约 N×120 秒，再加读取/评分耗时。50 次日预算仅按一轮一次请求估算，平均一天只够总计 50 次会话检查；20 个会话约 2.5 轮，岗位/额度/附件/回复复核还会消耗预算。不会因为改成轮转就变成持续覆盖多人。
- worker 心跳存在不代表处理任务有进度；后台有 paused/disconnected 标志，但前端主要展示运行中/已停止。
- 后端 monitor.note 仍说“不会自动外发”，前端开启提示也说“不自动外发”，而已有按会话自动外发实现；会误导用户。RecruitingOverview 仍有“单候选人试运行”文案，README/RECRUITING 仍称只监测当前选中会话。
- `_send_channel_status` 证明 Runtime/目标页存在，未证明当前打开目标候选人。browser.open_conversation 要求用户手动切到目标会话，因此多人监测覆盖与多人自动发送覆盖必须分别说明。

## 原问题文档中需要调整的地方

1. **更新版本与状态，不删除历史复核记录。** 176bf20 的模拟结果是该版本证据，应保留为历史；增加本次 5ceb7b8 的新表。128 项后端测试不能作为当前版本的验证数量，当前招聘测试为 176 项。
2. **保留“先修安全，再扩大招聘量”的顺序。** 当前持续招呼已有代码，但不能因为功能先实现就跳过额度、身份、恢复和停止验收。
3. **拆分实时性与预算目标。** 每 120 秒只读一个会话是预算受限的轮询兜底；被动消息监听仍是待验证方案。需定义允许的延迟、日预算耗尽后的行为和人工提示。
4. **澄清刷新约束。** “不擅自刷新已绑定页”与持续招呼每轮 reload 冲突。合理规则可区分消息监测页和用户主动启动的推荐页任务，具体能力与授权需在界面说明。
5. **“全天额度调度”分成两个验收层次。** 反复轮次直到当日额度/无候选人/停止是一层；跨日唤醒、重启恢复、无候选人后延迟再试是另一层。原需求目前没有明确必须自动跨日运行，不能把缺少跨日守护都判成业务 bug。
6. **停机验收写明可做到的边界。** 取消等待、阻止后续请求/模型/点击是可实现要求；已经发出的请求或点击不能保证即时撤销。
7. **已有资料与新消息分别调度。** “没有新消息不调用回复模型”合理，但配置/JD变化后的评分任务不应依赖候选人再发消息。
8. **不要把技术假设写成已验证事实。** WebSocket 捕获范围、增量 ID/排序契约、全联系人 DOM 覆盖和后台消息可用性仍需实测；默认间隔不能标成账号安全保证。

## 建议修复和验收顺序

1. 修浏览器目标/账号身份、统一岗位授权、普通回复和招呼的事务性外发占用与恢复。
2. 修额度跨日与并发基线、自动回复额度原子计数、最后点击前统一守卫和待核实人工闭环。
3. 修无新消息的身份与评分回归、历史覆盖路径、评分/附件跨进程任务占用。
4. 补全当前任务取消、账号暂停错误传播、监测实时性/预算/联系人范围与文案。
5. 将上述复现转为正式回归测试，尤其覆盖两个独立服务共用 DB、服务在活动任务期间启动、同 URL不同 target、无新消息但配置变化、取消发生在长请求期间。
6. 按原清单做最小样本真机验收，记录提交版本、账号/页面/岗位/会话身份、请求次数、回执和数据库状态，再逐步扩大规模。面试邀约禁发边界继续保留。
