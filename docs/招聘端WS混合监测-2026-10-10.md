# 招聘端 WS 优先、HTTP 兜底监测

## 行为

- 启用原有消息监测开关后，worker 每 10 秒读取一次**本机 Browser Runtime**的监听结果。这不是每 10 秒调用 BOSS HTTP 接口。
- Browser Runtime 用 CDP Network 事件被动观察已绑定招聘标签页的现有 `/chatws` 连接，解析 MQTT + Protobuf，只保留消息 ID 和双方身份，不保存正文、原始帧或登录数据。
- WS 正常时，停止定时轮询空会话。已确认绑定、勾选开放岗位且岗位自动任务未暂停的候选人消息触发原有 HTTP 同步、简历读取、模型和回复流程。
- 相同消息按账号、候选人、来源和消息 ID 去重；同一会话的通知合并。通知队列落本地数据库后才推进读取游标；处理中再收到消息不会被完成动作覆盖。
- 初次接入、重连、Runtime 重启、通知队列溢出、新增授权会话，会安排逐个 HTTP 补同步。补同步仍遵守共享请求节流与每日预算，不会并发突发读取所有会话。
- 没有新通知时，未完成的生成任务和等待打开 BOSS 对话的草稿仍按原有监测间隔重试。人工接管只同步与读取简历，不进行模型生成、评分或自动发送。

## 断线与安全

- 浏览器/绑定标签关闭，WS 断开、帧错误、协议无法确认，或者 WS 超过 90 秒没有收到有效数据，切回 HTTP。监听线程超过 35 秒没有更新，本地调度也会回退。
- HTTP 沿用原有间隔（默认每处理一个会话后等待 600 秒）、操作节流、每日预算和账号验证。切换后按该调度继续，不代表立即发起请求。
- HTTP 登录凭证失效或平台拒绝请求时仍暂停；验证/限制页面、BOSS 业务接口 403/429 触发统一暂停和至少 30 分钟冷却，不会借兜底通道继续请求。
- WS 恢复后补同步遗漏消息；HTTP 仍用于完整上下文、附件、生成后核实和发送前检查。
- 实际发送仍要求浏览器可用、人工选中对应会话以及原有全部检查；不自动切换会话，不通过 WS 发送。

## 生效与前端

需要重启 **Web、recruiting-worker 和本项目 Browser Runtime（cdp-proxy.mjs）**，让三者载入新代码。前端已构建。

在「运行记录」可看到“WS 监听中 / HTTP 轮询中 / 已暂停”和切换原因；沟通详情也显示 WS 等待状态。

如果监听接入前 WS 已经建立，CDP 可能只能给出后续帧，无法给出该连接的地址。本版本保留 HTTP 轮询，直到捕获可确认的新连接。前端提示时，可在监听已启动后**手动刷新已绑定的 BOSS 沟通页一次**；程序不自动刷新或创建连接。刷新后如需外发，请重新手动选中目标会话。

用于分析的 9444 独立浏览器不是项目默认连接；实现使用项目配置和已绑定招聘标签页。

## 自己发送消息的同步与沟通页布局修复

- 被动观察同一已绑定 BOSS 标签页的 WS 收发帧，分别维护 MQTT 缓冲，发出帧不会计为服务端连接健康。
- 通过绑定账号 UID 和候选人 UID/source 判断双向消息；自己发送的消息、服务端回传的本人消息均可触发原有 HTTP 同步。WS 不直接写入消息正文，不将发送尝试认定为平台发送成功。
- HTTP 仍遵循既有节流与预算，内容以平台读取为准。监听需要监测开启、已绑定会话且岗位在允许范围内；浏览器关闭后仍退回 HTTP 轮询。
- 回复及邀约处理记录区域限制高度为 360px，可滚动及键盘访问，保留完整历史；右侧主体允许收缩，防止记录不断撑长页面。
- 本次验证：Node WS 15 项、Python WS 调度 23 项、前端沟通页面 29 项通过，前端构建成功。隔离 Chrome 使用 200 条合成记录，在 1440/1000/600px 宽度下验证区域高度均为 360px、完整 200 条记录可滚动访问。未执行 BOSS 真实外发。

## PR #4：WebSocket 控制帧兼容

- 原作者指出非二进制帧统一触发协议错误，导致合法 ping/pong/close 控制帧也使监听失败。
- 收发方向的 ping/pong（opcode 9/10）均直接忽略，不写入 MQTT 分片缓冲，不改变已解析通知，不单独建立或延长 MQTT 健康状态。
- close（opcode 8）移除对应连接并退回 HTTP，保留已捕获的通知；新连接可以正常恢复监听。
- 无法识别的应用数据仍触发 HTTP 回退，保持原有容错策略和节流配置。
- 新增 5 项离线测试，覆盖双向控制帧、分片期间插入控制帧、超时、关闭重连及未知应用帧；Node WS 测试共 20 项通过。本次控制帧修复未新增 BOSS 真机验证。
