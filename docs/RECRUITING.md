# 招聘端目标与当前进度

更新日期：2026-10-08。本文件区分最终产品目标、已实现功能及当前试运行限制。

## 产品目标

以一个公司、一个 BOSS 招聘账号为起点，帮助招聘方完成面试前的找人、沟通和安排：

1. 读取平台已发布岗位，由人工勾选允许自动处理的开放岗位。
2. 按岗位寻找候选人、主动打招呼。最终目标是使用当天可用额度，也可配置每日自定义上限；平台限制、异常与暂停状态优先于额度目标。
3. 结合已读取的双方对话、公司说明、当前岗位 JD、简历及有效评估回复候选人，资料不足时明确待确认。
4. 收到简历后自动读取并按岗位 JD 评估，保留原文证据、版本和待追问事项。
5. 协调线上或线下面试、时间、地点或会议信息，确认后向人工交接。

不承担实际面试、面试评价、定薪、Offer、录用决定或入职管理。公司资料采用一个说明文本框加各岗位 JD，不扩展为复杂知识管理系统。模型只评价岗位相关的职业证据，不使用年龄、性别、婚育或外貌进行筛选。

## 当前实现

| 模块 | 已实现 | 尚未完成或限制 |
|---|---|---|
| 岗位 | 本地登录状态读取岗位、人工勾选、额度配置、读取今日剩余额度；事务内核对岗位与预占额度；推荐页绑定 target 和账号，持续点「打招呼」并核对回执 | 当前修复版本需重新做最小样本真机验收；持续循环依附 Web 进程，未实现跨日、重启后自动继续的全天任务 |
| 界面 | 工作台、岗位与额度、主动打招呼、候选人沟通、公司说明、模型设置 | 页面入口不代表对应平台动作已通过验收 |
| 会话 | 绑定多个会话；历史按平台消息 ID 合并；滚动累计可加载的联系人；按平台岗位 ID 关联并支持人工重新关联 | DOM 列表不证明覆盖全账号；未关联岗位不进入自动任务；增量排序和断线覆盖仍需平台验证 |
| 简历 | 下载已收到的 PDF，逐页提取文字，记录页数和完整性 | 缺文字页逐页走 OCR 兜底（需安装 `ocr` 可选依赖）；混合 PDF 保留文字层，OCR 未完成的页明确提示；文字提取不等于人工核对完整 |
| 自动评分 | 新附件缓存复用；按候选人、资料、平台岗位、JD 和模型配置去重；SQLite 任务占用阻止 Web/worker 重复调用模型 | 真实模型质量尚未完成验收；缺模型或 JD 时等待，失败保留资料并提供重试 |
| 回复 | 指定会话上下文生成草稿；发送前版本、账号和停止检查；自动外发预算原子预占；待核实记录阻止后续外发，可填写平台依据人工处理 | 自动外发已实现，真实发送闭环尚未完整验收；人工核实不触发自动重试 |
| 面试安排 | 候选人详情内保存线上或线下安排 | 当前测试明确禁止发送面试邀约，也禁止借普通回复发送邀约 |
| 监测 | 每轮轮转一个已勾选开放岗位下的允许会话；独立 worker、心跳、状态持久化；回复待处理任务持久化；停止可中断等待及后续步骤 | 按用户确认继续使用 HTTP 轮询，不解析二进制 chatws；一轮覆盖时间随会话数增加，受账号共用请求预算约束 |

自动评分的状态包括等待模型、等待 JD、读取中、评分中、完成、失败及暂停。停止联系、人工接管或岗位暂停会阻止自动处理。同一输入的失败不会在每轮监测反复调用模型。未知项不伪造成零分或满分，未核实完整性时不输出确定的完整总分。

## 技术架构

本地单体应用：React + TypeScript + Vite 前端，Python Bottle 后端，独立 SQLite 招聘数据库。原求职业务仍保留，不复用其岗位表承载招聘候选人。

- `src/bosshunter/recruiting/api.py`：本机同源 JSON 接口 `/api/recruiting/*`。
- `service.py`：招聘流程、上下文、评分去重、监测和发送前校验。
- `local_session.py`：本地 Chrome 登录 Cookie 仅在内存使用，通过后台 HTTP 读取岗位、绑定会话和 PDF。
- `browser.py`：复用原项目 `RuntimeClient → Node Browser Runtime → Chrome CDP`，已移除对 Kimi WebBridge 的运行依赖。
- `recommend.py`：用 patchright 连真实 Chrome（复用真实指纹/登录态），真刷新推荐页读取首卡候选人身份（跨刷新验证），并可对已确认候选人点「打招呼」（BOSS 自动发默认招呼语）后确认按钮变为「继续沟通」。
- `agent.py`：岗位证据评估与上下文回复，复用项目模型接口封装。
- `store.py`、`jobs.py`：招聘资料、已发布岗位、额度、发件箱和事件记录。

页面操作仅绑定已有的明确招聘标签页，不自动新建、导航、关闭或激活标签页，不自动切换聊天对象。可通过配置 `browser.recruiting_target_id` 指定目标；未指定时只接受唯一有效招聘页面，绑定失效后不会改用其他页面。Cookie 后台读取不要求页面操作服务在线；页面操作需要原项目 Runtime 与 Chrome 调试连接。

## 本地启动与验证

在原项目安装步骤基础上安装招聘可选依赖，并构建前端：

```bash
conda activate bosshunter
pip install -e '.[recruiting]'
npm --prefix src/bosshunter/web/frontend ci
npm --prefix src/bosshunter/web/frontend run build
bosshunter web --no-open
```

打开 `http://127.0.0.1:8686/recruiting`。模型接口和密钥在本地模型设置中配置。已有会话绑定向导，支持从联系人列表绑定多个候选人会话并切换当前，已真机验证。

回复监测可跑在独立进程（App 关闭后仍持续运行），另开一个终端：

```bash
bosshunter recruiting-worker
```

App 界面里「开启/停止消息与简历监测」通过控制标志（`monitor_enabled`）启停该 worker，worker 用「心跳」上报存活；worker 未运行时界面会提示先启动它。

招聘端后台请求使用本地 Cookie 读取 BOSS 接口，节流不能保证避免账号验证或封禁。当前配置及代码默认值为共用操作开始间隔 120–180 秒、同一操作内分页与联系人滚动间隔 15–30 秒、每日预算 100 次、每 600 秒轮转一个候选人、招呼间隔 120–180 秒、每岗每轮 1 个、自动回复默认每日 5 条。分页、发送前 HTTP 读取、浏览器账号核验及主动联系人/推荐页加载均进入预算；平台页面自行产生的后台请求未计入。403/429 触发至少 30 分钟的共享冷却，尊重更长 Retry-After；预算耗尽立即暂停 worker。冷却结束后须手动重新开启自动监测。Web 和 worker 重启后使用新的启动配置，此次参数由用户确认，详见 [审查清单修复](招聘端审查清单修复-2026-10-08.md)。HTTP 消息轮询保留，未改为 chatws。联系人列表通过浏览器 DOM 读取与滚动加载；加载动作与 HTTP 请求分别统计，一次滚动不代表一次接口请求。

```bash
PYTHONPATH=src python -m unittest discover -s tests -p 'test_recruiting*.py'
npm --prefix src/bosshunter/web/frontend test
```

招聘后端最近一次回归 277 项通过；68 项前端测试通过，前端生产构建通过（原 Dashboard 的 500 kB chunk 提示仍在）。使用 conda 环境、临时数据库和合成数据，没有调用真实 BOSS 或模型、没有发送真实消息。第二轮 13 项代码问题、混合 PDF 缺口以及后续界面状态遗漏已逐项修复并测试，详见 [二次审查与修复记录](招聘端二次代码审查-2026-10-07.md)。后续人工确认标记、简历版本选择和回复模型变更 3 项问题及接管后相同正文保存的边界情况也已修复，交回 Agent 后同正文恢复、环境变量模型接口地址影响评分缓存、取消与领取任务竞争，以及同平台岗位改名后重新关联的问题也已修复；随后修复了模型输出校验失败后的重复调用和同岗位改名后关联按钮被禁用的界面遗漏，见 [剩余问题复核与修复](招聘端剩余问题复核-2026-10-07.md)。

人工接管或暂停自动任务允许编辑、保存及明确发送普通回复；停止联系始终禁止外发。候选人工作列表只展示已勾选岗位，历史待核实外发仍保留入口。自定义上限不能替代平台额度读取，读取失败必须停止。长操作期间可提交停止、接管或关闭自动外发；已提交的平台动作不能撤销。相同上下文回复和评分通过数据库任务占用避免并发重复调用模型。

一个招聘数据库对应一个招聘账号，预算和任务占用由 Web 与 worker 共用。账号切换需使用独立数据库重新绑定，当前没有多账号分区。停止会阻止后续请求、评分和提交点击；已发出的 HTTP/模型请求需等待自身超时，已经提交的平台动作不能撤销。联系人覆盖、增量历史、岗位编辑页 ID、账号核对和真实发送回执仍需真机验证，模拟通过不等于平台验收。

最终业务验收终点是：一个真实岗位完成找人或接收新招呼、上下文沟通、简历评估、面试邀约确认及人工交接。当前最小样本测试的禁发邀约限制仍有效，不能以最终目标为由直接开放发送。
