以下为取消竞争修复前的证据。

P1，2026-10-07 后续只读复查确认。`api.py` 的 `outbox/cancel` 先通过 `store.row` 检查 status=draft，再调用无条件 `store.finish(..., cancelled)`；两步不是同一事务。Web 的服务锁不能阻止独立 worker 在中间调用 `store.claim` 将记录改为 sending。

合成复现：Web 读到 draft → worker 领取并变为 sending → Web 按旧检查结果写入 cancelled。之后 worker 的 `_send_guard` 只检查停止标志、权限和依据，没有检查动作状态，仍然通过。故界面可以报告“已取消”，正在运行的发送流程却未因此被拦住；取消状态还会使该动作脱离 sending/uncertain 的保护。

隔离脚本 `/private/tmp/recruiting_cancel_race_probe.py` 用 conda、临时 SQLite、两个服务和假浏览器命中该错误路径，没有调用平台或真实发送。这里只证明代码存在该竞争，不声称实际发生过误发。

修复应将“仅允许取消 draft”落实为事务内条件更新，并让最终发送校验验证动作仍处于合法阶段；不能无条件覆盖已领取、已提交或待核实记录。目前已修复，见上方结果。HTTP 轮询保持不变。

## 最新复查：两项问题及修复结果

此前三项修复完成后再次只读复核，新增确认以下两项，现均已修复；并非声称所有 bug 都已找完。下列描述保留修复前证据。原隔离复现脚本 `/private/tmp/recruiting_followup_review.py` 使用 conda、临时数据库、合成模型和假浏览器，两个不正确行为均命中，没有真实外发。

1. **P2：交回 Agent 后，同正文回复仍失效并重复调用模型。** 上一轮将接管前未提交草稿改为 expired，修复了接管后人工保存相同正文；但交回 Agent 后，原 reply_work 仍引用该草稿。每轮监测再次调用模型，如果正文和依据未变，`Store.draft` 不恢复 expired AI 草稿。测试先生成一次、接管、交回，然后监测两轮：模型总计调用 3 次，草稿仍 expired，不能发送。这是上一轮修复遗漏的自动恢复边界。
2. **P2：环境变量中的实际模型接口地址变化，评分仍复用旧结果。** 当实际地址来自 `ANTHROPIC_BASE_URL` 时，修改该变量会改变调用接口，但 `assessment_input` 的去重签名没有包含解析后的实际接口地址。测试用两个 `.invalid` 合成地址分别作为有效端点，真实解析结果发生改变，当前评分 ID 仍不变，再评分仍不调用模型。这里只证明缓存有效性错误，没有实际访问两个地址。

两项现已逐项修复：

- 交回 Agent 后，重新生成的相同有效正文可以恢复未提交的 expired 草稿；后续轮询复用恢复后的草稿，不重复调用模型。取消、已发送、执行中和待核实动作不恢复。相关 115 项回归通过。
- 评分去重包含解析后的实际模型接口地址及服务类型，并固定配置快照。实际地址改变后旧评分失效，重新评分产生新有效评估；明确配置地址覆盖环境变量时，不因无关环境变量变化而重复评分。相关 125 项回归通过。

旧评分记录仍保留；修复后会按包含实际地址的新输入签名重新评估，避免将无法确定当时实际接口的旧签名视为当前有效。

## 1. P1：相同正文的草稿去重会丢失 AI 的人工确认标记

位置：`store.py` 的 `draft`，`service.py` 的 `prepare_reply` 与 `_auto_send_if_allowed`。

发件箱按会话、动作、消息上下文和正文去重，不包含来源及依据。先保存人工普通回复，再生成正文相同且 `needs_human=True` 的 AI 回复时，`store.draft` 返回原人工草稿及原 refs。新的人工确认标记和缺失信息被丢弃。自动发送检查返回的旧 refs，因没有 `needs_human` 而允许执行。

复现结果：返回草稿 ID 与人工草稿一致，refs 无人工确认标记；自动发送调用了假浏览器并得到 sent。此证据只证明代码路径，不证明发生过真实误发。

修复应保留严格人工确认要求，避免同正文不同来源或依据共享不兼容的草稿权限；不能复活已发送或待核实动作。

## 2. P2：简历保存 A → B → A 时，当前资料仍是 B

位置：`store.py` 的 `save_document`，`service.py` 的 `reply_context` 和 `assessment_input`。

相同来源和内容的简历使用 INSERT OR IGNORE 去重，重新保存 A 返回原 A 记录，不更新当前版本选择。下游按创建时间和 rowid 取最新，仍选后创建的 B。

复现结果：第三次保存返回 A 的 ID，但当前回复上下文的简历 ID 为 B。页面、评分与回复会继续使用 B，违背刚保存的版本。

修复应明确记录当前生效资料，不应因内容已缓存而忽略本次选择；历史资料和评估保留。

## 3. P2：未有简历的会话更换模型后仍复用旧 AI 草稿

位置：`service.py` 的 `prepare_reply` 和 `reply_context_signature`。

草稿复用签名包括消息、公司、岗位、简历和评估，没有回复模型配置。没有简历时，模型变更也不会通过有效评估变化间接影响签名。因此配置从 synthetic-old 改为 synthetic-new 后，再次生成回复仍返回旧草稿，没有调用新模型。

复现结果：两次生成返回同一草稿 ID，模型调用总数为 1。

修复应将影响回复生成的模型配置纳入输入有效性判断，确保不同模型输入不误用相同缓存，并保留跨进程去重；不向前端暴露凭据。

先修第 1 项人工确认标记丢失，再修当前简历版本选择，最后修模型变更后的草稿有效性。每项反向验证修复后的行为，再运行相关招聘回归。业务规则均沿用用户已确认要求，不新增筛选、自动切换会话或邀约发送。
