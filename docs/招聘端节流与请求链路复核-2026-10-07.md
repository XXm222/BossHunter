# 招聘端节流与请求链路复核

仅招聘端。2026-10-07，根据用户反馈 BOSS 对接口调用敏感，检查后端请求链路和前端 JS 后调整保守试运行配置。没有请求真实 BOSS、模型或发送消息，没有重启正在使用的服务。

## 确认的问题及修复

1. 原等待按单次操作执行，分页请求只等待 5 秒；Web 和 worker 的等待相互独立。现在每个后台 HTTP 请求都进入同一招聘数据库的事务限速，包含会话分页、岗位分页、附件、联系人详情、额度和账号核验。计数与下一次可请求时间原子写入，等待期间不持有数据库事务；其他进程或重启不能重置该时间。
2. 发送前 `throttle=False` 会跳过旧等待。现在此参数仅保留调用兼容性，发送前读取也必须进入逐请求限速；浏览器内账号核验请求同样进入共用预算。冷却在最终发送守卫和招呼提交前再次检查。
3. 联系人滚动加载最多尝试 200 次、间隔 0.8 秒，可能触发额外平台加载。现在最多 10 次，真实浏览器每次滚动前都进入共用预算和限速；覆盖范围仍明确为页面可加载联系人，不声称全账号完整。
4. 推荐页刷新、选择岗位及招呼动作可能触发浏览器原生请求。现在主动触发这些动作前也进入共用预算；等待放在招呼占用之前，避免单纯限速/预算失败产生错误的“发送结果待核实”。额度及岗位条件在等待后再次核对。账号验证异常不再被吞掉后继续下一个岗位。
5. 原 HTTP 403/429 被当作普通读取失败，worker 可能继续下一轮。现在暂停自动监测、停止当前招呼流程，记录至少 30 分钟的跨进程共享冷却；较长 `Retry-After` 也被尊重。后台 HTTP 与浏览器账号核验两条路径均覆盖。等待者及最终发送检查遵守冷却，重启不会清除；冷却结束不会自行开启监测。每日预算耗尽立即暂停 worker，不再先反复报错三次。
6. 前端 15 秒状态轮询没有单独保护慢请求，可能重叠。现在共用一个进行中的本地状态请求；隐藏页面不轮询，保存或停止操作后等待旧请求结束再读取最新状态。该状态接口只读取本地数据库和本机 Runtime 状态，不直接请求 BOSS；保留 15 秒间隔以便及时显示暂停状态。
7. 绑定向导可在预览未完成时加载联系人，或者修改岗位名称后继续使用旧预览。现在保护向导请求不重叠，岗位改动撤销旧预览，迟到的旧结果被丢弃，确认绑定采用已预览的岗位名称。

## 当前配置

实际 `config.yaml`、示例配置和代码默认值已统一使用以下保守设置。已有数据库保存的自动回复上限仍优先于该配置默认值，按界面显示执行。

| 项目 | 值及含义 |
| --- | --- |
| `read_delay_min/max` | 120–180 秒；同一数据库内 Web/worker 共用的请求/主动加载动作间隔 |
| `read_daily_limit` | 保留实际配置原有的 20 次/日；每个分页和附件请求单独占用，主动浏览器加载、招呼动作也占用 |
| `read_page_delay` | 120 秒；独立 LocalBossSession 的分页等待，服务模式分页改用共用逐请求限速 |
| `monitor_interval_seconds` | 600 秒；每次只处理一个允许的候选人，完整一轮至少人数 × 10 分钟，处理耗时会进一步延长 |
| `greet_delay_min/max` | 120–180 秒；循环招呼动作之间的等待，共用请求限速另行执行 |
| `greet_per_job_min/max` | 每岗每轮 1 个 |
| `auto_reply_daily_limit` | 配置默认每日 5 条 |

重新启动 Web 与 `bosshunter recruiting-worker` 后使用新的启动配置；修改配置不会使旧进程的固定监测间隔自动刷新。HTTP 轮询机制仍保留，未增加二进制 chatws 解析；本轮按用户要求调整轮询频率。

20 次预算不等于可联系 20 人。一次资料读取、评分或发送闭环可能包含多个平台请求，因此预算可能在较少候选人时耗尽。

共用预算仅覆盖项目主动发起的 HTTP 请求及已标记的浏览器动作，不包含 BOSS 页面自行运行的 chatws、刷新请求、加载一个页面所产生的全部子请求或人工在 BOSS 内的操作。多个数据目录也不共用数据库限速；当前使用一个招聘账号对应一个数据目录。

这是降低调用量的保守配置，不能作为平台安全阈值或不封号保证。[BOSS 用户协议](https://www.zhipin.com/web/common/protocol/protocol-2019-09-30.html)对自动化获取数据等行为有约束；本轮未从平台取得安全频率承诺。真机验收仍按用户要求留到最后。

## 验证

正式新增测试为 `tests/test_recruiting_pacing.py`、前端 `BindingWizard.test.tsx` 及 `RecruitingPage.test.tsx` 中的请求竞争测试。使用临时 SQLite、可控时间、Mock HTTP、合成浏览器数据，不使用真实账号。

覆盖并发抢占同一请求时隙、重启后时间保留、等待不计数、停止中断、预算耗尽、每页限速、发送前禁止跳过、403/429 不重试、共享冷却、较长 Retry-After、浏览器账号核验拒绝、最终发送守卫、联系人加载边界，以及前端慢请求去重、隐藏页暂停、保存后新状态读取和过期绑定预览丢弃。

最终 conda 招聘后端 **267 项通过**，前端 **67 项通过**，生产构建及 `git diff --check` 通过。原 Dashboard 的 500 kB chunk 提示仍在。本轮新增 15 项后端节流测试和 5 项前端请求/预览测试；提交前发现绑定向导原有 5 项测试被新增测试覆盖，已恢复原有测试并保留新增测试；最终 67 项全部通过。复查结论针对请求链路及其关联状态，不代表全部后端逻辑和界面已穷尽检查，也不代表已经通过真机风控验收。
